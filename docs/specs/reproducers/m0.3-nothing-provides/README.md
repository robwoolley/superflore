# M0.3 — `Nothing PROVIDES` reproducer

Empirically confirms §2.2 of `docs/specs/bitbake-export-depends.md`
("A `-native` variant only exists if superflore said so") on the same
**wrynose** (6.0.3) environment used for the M0.2 reproducer.

## The scenario

`meta-repro2/classes/repro_native_gate.bbclass` is a byte-for-byte
reproduction of the real mechanism in
`meta-ros-common/classes/ros_superflore_generated.bbclass`, just renamed to
be ROS-independent:

```bitbake
BBCLASSEXTEND:append = "${@bb.utils.contains('GENERATED_BUILDTOOLS', '${BPN}-native', ' native nativesdk', '', d)}"
```

Two recipes:

* **toolU** — `inherit repro_native_gate`. Whether `toolu-native` exists at
  all depends entirely on whether `GENERATED_BUILDTOOLS` names it.
* **toolT** — `DEPENDS = "toolu-native"`, unconditionally
  `BBCLASSEXTEND = "native"` (toolT is always a real buildtool, like
  `rosidl_default_generators` always gets native-extended because superflore
  saw it as a direct `<buildtool_depend>` somewhere). Mirrors the real bug
  mechanism (§2.2): toolT needs `toolu-native` to exist, but whether it
  *does* exist is decided by a completely separate signal (whether some
  *other* package's direct `<buildtool_depend>`/`<buildtool_export_depend>`
  happened to also name toolU) — "only generated by luck."

## Before: `GENERATED_BUILDTOOLS` doesn't list `toolu-native`

```
$ bitbake -c populate_sysroot toolt-native
```

Result: **hard failure**, not a silent gap —
[`build_log_failure.txt`](build_log_failure.txt):

```
ERROR: Nothing PROVIDES 'toolu-native' (but .../toolt_1.0.bb DEPENDS on or
otherwise requires it). Close matches:
  libtool-native
  mtools-native
  toolt-native
ERROR: Required build target 'toolt-native' has no buildable providers.
Missing or unbuildable dependency chain was: ['toolt-native', 'toolu-native']
```

This is the exact failure class §2.2 describes real meta-ros builds hitting
whenever a `-native` variant is needed by something but wasn't independently
listed in `ROS_SUPERFLORE_GENERATED_BUILDTOOLS`.

## After: `GENERATED_BUILDTOOLS = "toolu-native"`

Adding one line to `local.conf`:

```
GENERATED_BUILDTOOLS = "toolu-native"
```

and rebuilding succeeds cleanly —
[`build_log_success.txt`](build_log_success.txt):

```
NOTE: recipe toolu-native-1.0-r0: task do_populate_sysroot_setscene: Succeeded
NOTE: recipe toolt-native-1.0-r0: task do_populate_sysroot_setscene: Succeeded
NOTE: Tasks Summary: Attempted 30 tasks of which 28 didn't need to be rerun and all succeeded.
```

Nothing else changed — same recipes, same layer, same dependency graph.
The only difference is whether the *unrelated* variable that gates
`BBCLASSEXTEND` happened to name this specific package. That's precisely
the "only generated by luck" fragility §2.2 and the worked example in §2.4
describe: today, `ROS_SUPERFLORE_GENERATED_BUILDTOOLS` is fed only by each
package's own *direct* `<buildtool_depend>`/`<buildtool_export_depend>`
tags, so a package that's only ever needed *transitively* (as some other
buildtool's export) has no guarantee of ever being listed, and the failure
mode when it isn't is exactly this one.

## Reproduce

Uses `bitbake-setup` (see the M0.2 reproducer's README for the install
step) since the classic `poky` combo repo has no `wrynose` branch yet:

```sh
mkdir wrynose && cd wrynose
bitbake-setup init --non-interactive poky-wrynose poky distro/poky machine/qemux86-64
source bitbake-builds/poky-wrynose/build/init-build-env

bitbake-layers add-layer ../<this-dir>/meta-repro2

# before: should fail with Nothing PROVIDES 'toolu-native'
bitbake -c populate_sysroot toolt-native

# after: add the fix, should succeed
echo 'GENERATED_BUILDTOOLS = "toolu-native"' >> bitbake-builds/poky-wrynose/build/conf/local.conf
bitbake -c populate_sysroot toolt-native
```
